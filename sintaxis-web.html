00La arquitectura hexagonal

Puertos y adaptadores. Qué problema resuelve, por qué se dibuja así, y cómo se ve en tu proyecto ahora mismo.

El problema que viene a resolver

La arquitectura en capas de toda la vida se dibuja como una torta: UI arriba, lógica al medio, base de datos abajo. Las flechas de dependencia apuntan hacia abajo — cada capa usa la de abajo.

Suena ordenado, pero tiene una consecuencia incómoda: tu lógica de negocio termina dependiendo de Postgres. Para probar una regla tan tonta como «no vender más entradas que la capacidad» necesitás una base de datos levantada. Y el día que quieras cambiar de motor, o de ORM, tenés que meter mano en el código que define tu negocio — que es justo el que menos querés tocar.

La idea central: dar vuelta la flecha

La arquitectura hexagonal propone algo simple de decir y difícil de acostumbrarse: el núcleo no depende de nada; todo depende del núcleo.

¿Cómo se logra si el núcleo obviamente necesita guardar cosas? Con un truco de dos partes. El núcleo declara lo que necesita como una interface, y esa interface vive adentro del núcleo. Después, alguien afuera escribe la implementación.

// ADENTRO del núcleo: src/core/ports/IEventRepository.ts
// El dominio dice QUÉ necesita, en su propio idioma.
export interface IEventRepository {
  save(event: Event): Promise<void>;
  findById(id: string): Promise<Event | null>;
}

// AFUERA: src/infrastructure/repositories/DrizzleEventRepository.ts
// La infraestructura dice CÓMO, y para eso importa del núcleo.
//                                     ↓ la flecha apunta hacia adentro
import { IEventRepository } from '../../core/ports/IEventRepository';

export class DrizzleEventRepository implements IEventRepository { ... }

Fijate en el detalle: DrizzleEventRepository importa del núcleo. El núcleo no importa de Drizzle. La dependencia quedó invertida — de ahí el nombre formal, inversión de dependencias.

La diferencia en una línea

En capas: «el negocio usa la base de datos». En hexagonal: «el negocio declara un contrato, y la base de datos se ofrece a cumplirlo».

¿Por qué un hexágono?

Por nada en particular — y esto confunde a todo el mundo al principio. No hay seis capas ni seis nada. Alistair Cockburn, que inventó el patrón en 2005, lo dibujó como un polígono para poder mostrar varios lados sin sugerir que hay un «arriba» y un «abajo» como en las capas. Podría ser un pentágono.

El nombre técnico del patrón es Puertos y Adaptadores, y es mucho más honesto sobre lo que hace.

Los dos lados: driving y driven

Todo lo que rodea al hexágono cae en uno de dos grupos, y la pregunta que los separa es quién empieza la conversación.

Lado driving (izquierda)Lado driven (derecha)
También llamadoPrimario, de entradaSecundario, de salida

Puerto ≠ adaptador

La metáfora del enchufe es literal y sirve:

  • Puerto = la interface. El enchufe en la pared. Define la forma, no el aparato.
  • Adaptador = la implementación. El aparato que enchufás.

Y lo importante: un puerto admite muchos adaptadores. IEventRepository hoy lo cumple Drizzle contra Neon. Mañana lo puede cumplir un repositorio en memoria para tests, o uno contra MongoDB, o uno que devuelva datos falsos para una demo. El núcleo ni se entera de cuál está enchufado — y esa indiferencia es todo el punto del patrón.

Cómo saber si lo rompiste

La prueba del import

Abrí cualquier archivo dentro de src/core/. Si tiene un import de drizzle-orm, de next/server, o de cualquier cosa dentro de src/infrastructure/ — el hexágono está roto. Es literalmente la única regla que hay que vigilar, y se chequea en dos segundos.

El diagrama de tu sistema

Este es TicketHexa hoy, no un diagrama genérico. Hacé clic en cualquier pieza para ver qué archivos la componen y qué falta.

Fijate en un detalle que no es casualidad: ports/ vive dentro de core/, no dentro de infrastructure/. Uno esperaría que el contrato del repositorio esté cerca de la base de datos, pero justamente ahí está el truco del patrón. Si movés esa carpeta a infraestructura, el núcleo pasa a depender de afuera y el hexágono se desarma.

Hacia dónde pueden apuntar los imports

Cómo se chequea en dos segundos

Buscá import en toda la carpeta src/core/. Si todos los resultados apuntan a otro archivo de src/core/, está sano. Cualquier drizzle-orm, next/server o ../../infrastructure que aparezca ahí es una flecha que subió.

Lo que ganás, en concreto

  1. Testeás el negocio sin infraestructura. Para probar que CreateTicketUseCase no sobrevende, le pasás un repositorio falso en memoria. Cero Docker, cero Postgres, milisegundos en vez de segundos. Esto es la razón práctica por la que vale la pena.
  2. Postergás decisiones. Podés escribir todo el dominio antes de haber elegido base de datos. La elección de Neon es un detalle enchufado en la punta derecha, no un cimiento.
  3. El negocio se lee en un solo lugar. ¿Cuáles son las reglas de TicketHexa? Están en tres archivos de core/domain/entities, sin una línea de SQL ni de HTTP alrededor.

Lo que te cuesta

Seamos honestas: son más archivos y más rebote. Un POST que en Express serían 15 líneas acá pasa por una ruta, un DTO, un caso de uso, una entidad, un puerto y un adaptador. Para un CRUD de tres tablas sin reglas es sobre-ingeniería declarada.

Se paga solo cuando hay reglas de verdad — y «no vender más entradas que la capacidad, incluso con dos personas comprando al mismo tiempo» es exactamente ese tipo de regla. Ese es el motivo por el que TicketHexa es un buen caso para aprender el patrón: tiene una regla que justifica la ceremonia.

El recorrido completo de una petición

Así viaja hoy un POST /api/events, capa por capa:

1. Cliente POST /api/events con un JSON 2. Ruta route.ts lee el body, arma el DTO 3. Cableado new DrizzleEventRepository() → new CreateEventUseCase(repo) 4. Caso de uso execute(dto) coordina el flujo 5. Entidad new Event(...) valida — si algo está mal, lanza acá 6. Puerto repo.save(event) ← el núcleo habla en su idioma 7. Adaptador db.insert(eventsTable).values(...) ← recién acá aparece SQL 8. Postgres INSERT 9. Vuelta Event → NextResponse.json(..., { status: 201 })

Los pasos 1 a 4 y el 9 son intercambiables sin tocar el 5. El paso 7 es intercambiable sin tocar el 6. Eso es el hexágono funcionando.

01TypeScript: interface vs class

La confusión número uno al empezar. Son cosas distintas.

interfaceclass
¿Qué es?Una forma, un contratoUn plano que fabrica objetos
¿Existe en runtime?No — desaparece al compilarSí — es código JavaScript real
¿Tiene lógica?NuncaSí, métodos y validaciones
¿Se instancia?NoSí, con new
 
// INTERFACE: solo describe la forma de los datos. No hace nada.
interface LibroProps {
  id: string;
  titulo: string;
  paginas: number;
}

// CLASS: tiene comportamiento y protege sus reglas.
class Libro {
  constructor(props: LibroProps) { /* ... */ }
}

En el proyecto usás interface para tres cosas distintas:

  • XProps — forma de los datos que entran al constructor de una entidad.
  • XDTO — forma de los datos que llegan desde internet a un caso de uso.
  • IXRepository — contrato de un puerto.

El signo ? (opcional)

interface LibroProps {
  id?: string;       // puede venir o no → tipo real: string | undefined
  titulo: string;    // obligatorio
}
Trampa — aplica a tu Ticket

El ? en Props significa «el que me llama puede no mandarlo». Pero si el constructor siempre le asigna un valor, entonces la propiedad de la clase ya no es opcional. Son dos declaraciones separadas y no tienen por qué coincidir.

interface LibroProps {
  id?: string;                     // opcional al construir
}

class Libro {
  public readonly id: string;      // SIEMPRE existe después de construir ✅

  constructor(props: LibroProps) {
    this.id = props.id ?? crypto.randomUUID();
  }
}

Operadores ?? vs ||

valor ?? porDefecto   // usa porDefecto solo si valor es null o undefined
valor || porDefecto   // usa porDefecto si valor es CUALQUIER falsy:
                      // 0, "", false, null, undefined

Con 0 la diferencia importa: 0 || 10 da 10 (probablemente no era la idea), 0 ?? 10 da 0.

Union types — todavía no lo usás, deberías

Restringe un string a un conjunto cerrado de valores:

type EstadoPedido = 'pendiente' | 'enviado' | 'entregado';

let e: EstadoPedido = 'pendiente';  // ✅
let f: EstadoPedido = 'volando';    // ❌ error en tiempo de compilación

Con status: string el compilador acepta cualquier cosa. Con un union type, el error salta antes de ejecutar.

type vs interface

Prácticamente intercambiables para describir objetos. Convención razonable: interface para formas de objetos, type para uniones y alias.

02Clases: constructor, this, modificadores

El plano que fabrica objetos válidos, o no fabrica nada.

export class Libro {
  //  ┌── modificador de acceso
  //  │      ┌── inmutable tras el constructor
  public readonly id: string;
  public titulo: string;
  private codigoInterno: string;   // solo accesible dentro de la clase

  constructor(props: LibroProps) {
    this.validate(props);          // primero valida, después asigna
    this.id = props.id;
    this.titulo = props.titulo;
  }

  // MÉTODO PÚBLICO: comportamiento del dominio (camelCase)
  public renombrar(nuevoTitulo: string): void {
    if (nuevoTitulo.trim().length < 3) {
      throw new Error("Título muy corto");
    }
    this.titulo = nuevoTitulo;
  }

  // MÉTODO PRIVADO: reglas internas, nadie de afuera lo llama
  private validate(props: LibroProps): void {
    if (!props.titulo || props.titulo.trim() === '') {
      throw new Error("El título no puede estar vacío");
    }
  }
}

Atajo: parámetros de constructor como propiedades

Esto es TypeScript puro y ya lo usás en los casos de uso:

// Forma larga
class CrearLibro {
  private readonly repo: ILibroRepository;
  constructor(repo: ILibroRepository) {
    this.repo = repo;
  }
}

// Forma corta — idéntica.
// El modificador en el parámetro crea y asigna la propiedad.

  constructor(private readonly repo: ILibroRepository) {}
}

implements: firmar un contrato

export class DrizzleLibroRepository implements ILibroRepository {
  // Si falta un método del contrato, o cambia una firma,
  // TypeScript da error ACÁ, no en tiempo de ejecución.
  // Esa es la ganancia.
}

Validar en el constructor (invariante)

El principio central de las entidades ricas: si el objeto existe, es válido. No puede haber un Libro a medio construir dando vueltas, porque el constructor lanza antes de terminar.

const libro = new Libro({ titulo: "" });  // 💥 throw, el objeto nunca nace
Distinción clave para tu Event

Hay dos momentos de vida distintos y no comparten reglas.

MomentoQué pasa¿Vale «fecha futura»?
CreaciónEl usuario manda datos nuevosSí
ReconstituciónTraés una fila de la BD y la volvés objetoNo — el evento del año pasado existió

Si la regla de creación vive en el constructor, la reconstitución de datos viejos revienta. Patrón habitual para separarlas: el constructor valida solo lo estructural, y un método estático static create(...) agrega las reglas de creación.

class Libro {
  private constructor(props: LibroProps) { /* validación estructural */ }

  static create(props: LibroProps): Libro {   // camino "nuevo"
    // reglas que solo aplican a lo recién creado
    return new Libro(props);
  }

  static fromDB(props: LibroProps): Libro {   // camino "rehidratar"
    return new Libro(props);
  }
}

Guards de validación: cuidado con la lógica booleana

// ❌ Nunca lanza si el valor es "": "" es falsy,
//    el && corta y nunca llega al trim
if (props.campo && props.campo.trim() === '') throw new Error("vacío");

// ✅ Lanza si falta O si es solo espacios
if (!props.campo || props.campo.trim() === '') throw new Error("vacío");

// ✅ Versión compacta con optional chaining
if (!props.campo?.trim()) throw new Error("vacío");
Memorizar

Valores falsy en JS: false, 0, -0, "", null, undefined, NaN. Todo lo demás es truthy — incluidos [] y {}.

03Async / await y Promise<T>

Todo lo que toca la base de datos es asíncrono: se pide algo y la respuesta llega después.

// Promise<T> = "prometo devolverte un T más adelante"
async findById(id: string): Promise<Libro | null> {
  const filas = await db.select().from(librosTable);  // await = "esperá acá"
  //            ^^^^^ sin await, filas sería una Promise, no los datos
  return null;
}

Reglas:

  • Si una función tiene await adentro, tiene que ser async.
  • Una función async siempre devuelve una Promise, aunque escribas return 5.
  • Para consumir una función async: const x = await miFuncion();
El bug más común

Olvidar el await.

const evento = this.repo.findById(id);   // ❌ evento es una Promise
if (!evento) { }                         // nunca entra: una Promise siempre es truthy

const evento = await this.repo.findById(id);  // ✅

try / catch

try {
  const resultado = await algoQuePuedeFallar();
} catch (error: any) {
  // Cae acá cualquier throw de adentro del try,
  // sin importar cuán profundo esté
  console.error(error.message);
}

Un throw de tu entidad viaja hacia arriba: entidad → caso de uso → route handler, hasta el primer catch. Por eso las rutas API envuelven todo en try/catch: son la última barrera antes de que el servidor devuelva un 500 feo.

04Los 4 bloques del hexágono

El flujo, siempre en este orden.

Cliente → API Route → Caso de Uso → Entidad (reglas) ↓ Puerto (interface) ↓ Repositorio Drizzle → PostgreSQL
La regla de dependencias

Las flechas de import apuntan hacia adentro. infrastructure importa de core. core nunca importa de infrastructure. Si en un archivo de core/ aparece un import de Drizzle o de Next, el hexágono está roto.

A · Entidad src/core/domain/entities/

Reglas de negocio puras. Cero imports externos. Sabe decir «no» cuando le piden algo inválido.

B · Puerto src/core/ports/

Una interface que declara qué se puede hacer, sin decir cómo.

import { Libro } from '../domain/entities/Libro';

export interface ILibroRepository {
  save(libro: Libro): Promise<void>;
  findById(id: string): Promise<Libro | null>;
  findAll(): Promise<Libro[]>;
}

Fijate que el puerto habla en objetos de dominio (Libro), no en filas de SQL. Ahí está el aislamiento.

C · Caso de uso src/core/application/use-cases/

Coordina. No tiene reglas de negocio (eso es de la entidad) ni SQL (eso es del repositorio).

export interface CrearLibroDTO {   // lo que llega de afuera
  titulo: string;
  paginas: number;
}

export class CrearLibroUseCase {
  constructor(private readonly repo: ILibroRepository) {}
  //                                  ^^^^^^^^^^^^^^^^
  //   pide la INTERFACE, no la clase concreta. Esto es la inyección
  //   de dependencias: en tests le pasás un repo falso en memoria
  //   y probás la lógica sin levantar Postgres.

  async execute(data: CrearLibroDTO): Promise<Libro> {
    const libro = new Libro({ id: crypto.randomUUID(), ...data });
    await this.repo.save(libro);
    return libro;
  }
}

¿Por qué un DTO y no pasar el body crudo? El DTO es un filtro: define exactamente qué campos entran. Si el cliente manda { titulo: "x", esAdmin: true }, esAdmin se descarta porque no está en el DTO. Es una frontera de seguridad, no burocracia.

D · Adaptador src/infrastructure/repositories/

Firma el contrato y traduce entre el mundo de objetos y el mundo de tablas.

export class DrizzleLibroRepository implements ILibroRepository {
  async findById(id: string): Promise<Libro | null> {
    const filas = await db.select()
      .from(librosTable)
      .where(eq(librosTable.id, id));

    if (filas.length === 0) return null;

    // MAPEO: fila plana de SQL → objeto rico de dominio
    return new Libro({
      id: filas[0].id,
      titulo: filas[0].titulo,
    });
  }
}

Ese mapeo es el corazón del patrón. Nunca dejes escapar una fila cruda de Drizzle fuera de infrastructure/.

05Drizzle ORM

Definir tablas, consultar, y no borrar la base por accidente.

Definir tablas — src/infrastructure/db/schema.ts

import { pgTable, uuid, varchar, timestamp, integer } from 'drizzle-orm/pg-core';

export const librosTable = pgTable('libros', {
  //                                 ^^^^^^ nombre real de la tabla en Postgres
  id: uuid('id').defaultRandom().primaryKey(),
  titulo: varchar('titulo', { length: 255 }).notNull(),
  paginas: integer('paginas').notNull(),
  estado: varchar('estado', { length: 50 }).notNull().default('disponible'),
  creadoEn: timestamp('created_at').defaultNow().notNull(),
  //                   ^^^^^^^^^^ columna en snake_case, propiedad en camelCase
  autorId: uuid('autor_id').notNull().references(() => autoresTable.id),
});
ModificadorQué hace
.primaryKey()Clave primaria
.notNull()Prohíbe NULL
.unique()Sin duplicados
.defaultRandom()UUID automático (solo en uuid)
.defaultNow()Timestamp actual (solo en timestamp)
.default(x)Valor por defecto
.references(() => tabla.columna)Foreign key
Foreign keys y el orden de inserción

Si orders.userId referencia users.id, Postgres rechaza cualquier inserción con un userId que no exista en users. No importa que tu entidad esté perfectamente validada: la BD tiene la última palabra. Para insertar un ticket primero tiene que existir el usuario.

{ mode: 'date' } en un timestamp le dice a Drizzle que te devuelva un objeto Date de JavaScript en vez de un string.

Consultas

import { eq, and, gt } from 'drizzle-orm';

// SELECT * FROM libros
const todos = await db.select().from(librosTable);
// → devuelve SIEMPRE un array, aunque esté vacío

// SELECT * FROM libros WHERE id = ?
const uno = await db.select().from(librosTable).where(eq(librosTable.id, id));
// → TAMBIÉN un array, aunque traiga un solo elemento.
//   Por eso el patrón: if (uno.length === 0) return null; luego uno[0]

// INSERT
await db.insert(librosTable).values({ id, titulo, paginas });

// INSERT devolviendo la fila creada
const [creado] = await db.insert(librosTable).values({...}).returning();

// UPDATE ... WHERE  ← ¡el .where() no es opcional en la práctica!
await db.update(librosTable)
  .set({ titulo: 'nuevo' })
  .where(eq(librosTable.id, id));

// DELETE
await db.delete(librosTable).where(eq(librosTable.id, id));

// Condiciones compuestas
.where(and(eq(librosTable.estado, 'disponible'), gt(librosTable.paginas, 100)))
Peligro

Un update o delete sin .where() afecta todas las filas de la tabla. Drizzle no te va a detener.

Operadores frecuentes: eq (=), ne (≠), gt / gte (> / ≥), lt / lte (< / ≤), inArray, isNull, like, y los combinadores and / or / not.

Tipos inferidos

export type LibroRecord = typeof librosTable.$inferSelect;    // forma al leer
export type NewLibroRecord = typeof librosTable.$inferInsert; // forma al insertar

Si cambiás una columna del schema, estos tipos cambian solos y TypeScript te marca todos los lugares que hay que ajustar.

Comandos de drizzle-kit

npx drizzle-kit push      # aplica el schema directo a la BD (desarrollo)
npx drizzle-kit generate  # genera archivos .sql de migración (producción)
npx drizzle-kit migrate   # aplica las migraciones generadas
npx drizzle-kit studio    # GUI para ver/editar la BD en el navegador

En desarrollo push alcanza. En producción se usa generate + migrate porque deja historial versionado de los cambios.

06Next.js App Router: API Routes

El adaptador de entrada: donde el HTTP se convierte en llamadas al hexágono.

La regla de los nombres

En App Router la carpeta es la URL y el archivo se llama siempre route.ts:

src/app/api/venues/route.ts        →  /api/venues
src/app/api/venues/[id]/route.ts   →  /api/venues/cualquier-cosa
src/app/api/tickets/route.ts       →  /api/tickets

route.ts en singular. routes.ts no lo detecta el framework y la ruta simplemente devuelve 404.

Handlers = verbos HTTP exportados

Exportás una función async con el nombre del verbo, en MAYÚSCULAS:

import { NextResponse } from 'next/server';

export async function GET() { }
export async function POST(request: Request) { }
export async function PUT(request: Request) { }
export async function DELETE(request: Request) { }

Leer el body

Ojo

body es any. Todo lo que venga de internet es texto sin garantías: body.paginas puede ser "muchas", null o no venir. Hoy tu única defensa es la validación de la entidad — funciona, pero el error salta más adentro de lo ideal.

Parámetros dinámicos [id]

En Next 15+ params es una Promise y hay que esperarla:

export async function GET(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;   // ← sin el await, id sería undefined
}

Cableado del hexágono en la ruta

La ruta es el único lugar donde se conecta el mundo abstracto con el concreto:

export async function POST(request: Request) {
  try {
    const body = await request.json();

    const repository = new DrizzleLibroRepository();   // implementación concreta
    const useCase = new CrearLibroUseCase(repository); // se la inyectás al caso de uso

    const resultado = await useCase.execute({
      titulo: body.titulo,
      paginas: body.paginas,
    });

    return NextResponse.json({ data: resultado }, { status: 201 });
  } catch (error: any) {
    return NextResponse.json({ error: error.message }, { status: 400 });
  }
}
El premio de toda la arquitectura

Este es el punto exacto donde el hexágono se «enchufa». Cambiar Drizzle por otra cosa significa tocar solo esa línea, en ningún otro lado.

07Códigos de estado HTTP

La regla mental: 4xx = culpa del cliente. 5xx = culpa tuya.

CódigoSignificadoCuándo usarlo acá
200 OKSalió bienGET exitoso
201 CreatedRecurso creadoPOST exitoso
204 No ContentBien, sin cuerpoDELETE exitoso
400 Bad RequestEl cliente mandó mal los datosFalló la validación de la entidad
404 Not FoundNo existe el recursofindById devolvió null
409 ConflictChoca con el estado actualSin capacidad, sobreventa
422 UnprocessableBien formado pero inválidoAlternativa a 400
500 Server ErrorSe rompió el servidorBD caída, bug inesperado

Hoy todos tus errores caen en 400. El problema: catch recibe un Error genérico y no puede distinguir «capacidad insuficiente» (409) de «evento no existe» (404) de «la BD explotó» (500). La solución idiomática son clases de error propias:

export class LibroNotFoundError extends Error {
  constructor(id: string) {
    super(`Libro ${id} no encontrado`);
    this.name = 'LibroNotFoundError';
  }
}

// En la ruta, el catch ya puede decidir:
catch (error) {
  if (error instanceof LibroNotFoundError) {
    return NextResponse.json({ error: error.message }, { status: 404 });
  }
  return NextResponse.json({ error: "Error interno" }, { status: 500 });
}

10Errores que ya cometiste (o casi)

Guardá esta lista, son los que más se repiten.

  1. Import fantasma — import { error } from "console" que nunca se usa. El linter lo marca; borralos.
  2. && donde va || en un guard — if (x && x.trim() === '') nunca detecta "". Repasá los valores falsy en la sección 02.
  3. Doble ;; — no rompe nada, pero delata copy-paste.
  4. excecute vs execute — un typo en un nombre de método convierte dos clases que «hacen lo mismo» en dos clases incompatibles. TypeScript no te avisa porque no hay interface que obligue.
  5. Método en PascalCase — SellTicket() parece un constructor. Métodos siempre en camelCase.
  6. routes.ts en vez de route.ts — Next no lo registra y la ruta devuelve 404 sin ningún error visible.
  7. Falta de await — la variable queda con una Promise adentro y toda condición sobre ella es truthy.
  8. Import no usado en el schema (decimal) — ruido que confunde al leer.
  9. Validar reglas de creación en el constructor — rompe la reconstitución desde la BD. Ver sección 02.
  10. .env* en .gitignore — también ignora .env.example, que sí querés versionar. Se arregla con una línea de excepción !.

Traducción práctica de la jerga, agrupada por tema. Cuando una palabra aparece en tu código, se dice dónde.

Arquitectura y diseño

TérminoTraducción práctica
EntidadObjeto con identidad propia y reglas que se autoprotegen. Dos entradas con los mismos datos pero distinto id son entidades distintas.
Entidad ricaEntidad que además de datos tiene comportamiento y validación. Lo contrario es el modelo anémico: una bolsa de propiedades públicas sin ninguna regla, donde la lógica termina desparramada por todos lados.
Value ObjectObjeto de dominio sin identidad: vale por su contenido, no por quién es. $5.000 CLP es intercambiable con cualquier otro $5.000 CLP. Se usa para conceptos con reglas propias (Dinero, Email) que hoy tenés como number o string sueltos.
AggregateGrupo de entidades que se modifican como una sola unidad y comparten una regla que las abarca. En TicketHexa, «evento + sus tickets» es el candidato natural: la regla de no sobrevender los cruza a los dos.
Raíz del aggregateLa única entidad del grupo a la que se le habla desde afuera. Nadie modifica un ticket sin pasar por su evento.
PuertoInterface que define qué se necesita, sin decir cómo. El enchufe de la pared.
AdaptadorClase concreta que implementa un puerto con tecnología real. El aparato que enchufás.
Driving / drivenLos dos lados del hexágono. Driving (primario) es quien te llama: HTTP, CLI, tests. Driven (secundario) es lo que vos llamás: base de datos, email. La pregunta que los separa: quién empieza la conversación.
RepositorioEl patrón que hace que guardar y buscar objetos parezca una colección en memoria, escondiendo que abajo hay SQL. Por eso los métodos se llaman save y findById y no insert o select: el dominio pide en su idioma, nunca en el de la base. Es el puerto de salida más común, y en tu proyecto son las tres interfaces I*Repository.
Servicio de dominioLógica de negocio que no cae naturalmente dentro de ninguna entidad porque involucra a varias. Ojo: es la excusa favorita para vaciar las entidades. Usalo solo cuando de verdad no hay dueño claro.
Caso de usoCoordinador de un flujo completo. Busca, le pide a la entidad, guarda. No tiene reglas ni SQL. También lo vas a ver como application service o interactor.
DTOData Transfer Object. Una interface plana que describe los datos que cruzan una frontera, sin comportamiento. Cumple dos funciones: documenta qué espera cada capa, y filtra — lo que no está declarado en el DTO no entra. Es la diferencia entre recibir body crudo de internet y recibir exactamente los tres campos que te importan.
Inyección de dependenciasRecibir lo que necesitás por constructor en vez de fabricarlo adentro. Es lo que te permite pasar un repositorio falso en los tests.
Inversión de dependenciasLa regla que hace posible todo el patrón: la interface vive del lado del que la usa (el núcleo), no del que la implementa (la infraestructura). Por eso ports/ está dentro de core/.
InvarianteRegla que siempre debe cumplirse mientras el objeto exista. «La capacidad nunca es negativa». Se protege validando en el constructor y en cada método que muta.
ReconstituciónRearmar un objeto de dominio desde datos guardados. Distinto de crearlo: las reglas de creación no siempre aplican al rehidratar. Ver sección 02.
MapeoTraducir entre fila de base de datos y objeto de dominio, en las dos direcciones. Vive en el adaptador y en ningún otro lado.
Modelo anémicoEl antipatrón: entidades que son solo propiedades públicas, con toda la lógica en servicios externos. Se reconoce porque las clases del dominio no tienen ni un solo método.

TypeScript

TérminoTraducción práctica
InstanciarUsar new sobre una clase para fabricar un objeto real en memoria. La clase es el plano; la instancia, la casa.
implementsDeclarar que una clase cumple un contrato. Si falta un método o cambia una firma, el error salta al compilar y no en producción.
Union typeUn tipo que solo admite valores de una lista cerrada: 'pendiente' | 'pagado'. Convierte un error de datos en un error de compilación.
NarrowingAchicar un tipo amplio a uno concreto dentro de un bloque, usando typeof, instanceof o un if. Es lo que te deja usar unknown con seguridad en vez de any.
Type guardLa condición que hace el narrowing. if (error instanceof EventNotFoundError) es un type guard.
GenéricoUn tipo que recibe otro tipo como parámetro: Promise<Event>, Array<string>. Sirve para escribir una vez algo que funciona con cualquier tipo sin perder el tipado.
Parameter propertyEl atajo constructor(private readonly repo: IRepo) {}: el modificador en el parámetro crea y asigna la propiedad de una. Ya lo usás en los tres casos de uso.
readonlyLa propiedad se asigna una vez en el constructor y después no se puede cambiar. Se usa para el id: la identidad de una entidad no muta.
Truthy / falsyCómo se comporta un valor en un if. Falsy: false, 0, "", null, undefined, NaN. Todo lo demás es truthy, incluidos [] y {}.
Optional chaining ?.Accede a una propiedad solo si el objeto no es null/undefined; si lo es, devuelve undefined en vez de reventar.
Nullish coalescing ??Valor por defecto que se aplica solo ante null o undefined — a diferencia de ||, que también salta con 0 y "".
Structural typingTypeScript compara tipos por su forma, no por su nombre. Si un objeto tiene los métodos que pide una interface, la cumple aunque nunca haya escrito implements. Por eso un repositorio falso funciona sin heredar de nada.

Asincronía

TérminoTraducción práctica
PromiseUn valor que todavía no llegó. Promise<Event> es «te prometo un Event más adelante».
awaitDesempaqueta la promesa: frena ahí hasta que el valor esté. Sin él te quedás con la promesa en la mano, que siempre es truthy.
Condición de carreraDos operaciones simultáneas que leen el mismo estado y ambas deciden que pueden seguir. Es exactamente el riesgo de sobreventa: dos compras leen capacity = 1, las dos validan bien, las dos venden.
Bloqueo optimistaUna de las curas de la carrera: guardás una columna version y el UPDATE exige que no haya cambiado. Si otro llegó antes, tu update no afecta ninguna fila y sabés que perdiste.

Base de datos

TérminoTraducción práctica
ORMObject-Relational Mapper. Traduce entre objetos de tu lenguaje y tablas de SQL, con tipado. Drizzle es el tuyo.
SchemaLa definición de tus tablas en código. En tu proyecto, src/infrastructure/db/schema.ts. Es la fuente de verdad de la estructura de la base.
MigraciónUn archivo con los cambios de estructura de la base, versionado igual que el código. Permite reproducir la misma base en cualquier máquina y volver atrás si algo sale mal.
push vs generatepush aplica el schema directo a la base — cómodo en desarrollo, sin historial. generate + migrate crea los .sql versionados — es lo que se usa en producción.
Foreign keyUna columna que obliga a que su valor exista en otra tabla. Postgres la hace cumplir aunque tu código no la valide: la base tiene la última palabra.
TransacciónUn grupo de operaciones que ocurren todas o ninguna. Es lo que le falta hoy a CreateTicketUseCase: descontar capacidad y guardar el ticket son dos viajes sueltos.
AtomicidadLa propiedad que garantiza la transacción: no existe un estado intermedio visible. O se hicieron las dos cosas, o ninguna.
RollbackDeshacer todo lo hecho dentro de una transacción que falló, dejando la base como estaba antes de empezar.
UUIDIdentificador único de 128 bits generado sin coordinación central. Ventaja sobre un id autoincremental: lo podés generar en el dominio, antes de tocar la base — que es exactamente lo que hacés con crypto.randomUUID().
NormalizaciónSeparar los datos en tablas para no repetir información. Tener venues aparte de events en vez de repetir la dirección en cada evento es normalización.
Tabla intermediaLa que rompe una relación muchos-a-muchos en dos de uno-a-muchos. orders es la tuya: conecta usuarios con eventos y además guarda datos propios de la compra.
ServerlessLa base se enciende cuando la usás y se apaga sola. Pagás por uso, no por tiempo encendida. Es lo que hace Neon, y por eso el driver es HTTP en vez de una conexión persistente.
SeedScript que llena la base con datos de prueba. Te va a hacer falta apenas tengas usuarios, porque sin un user en la tabla no podés insertar ningún ticket.

HTTP y API

TérminoTraducción práctica
RESTUn estilo de API donde las URLs nombran recursos (sustantivos) y el verbo HTTP dice qué hacerles. POST /api/events, no /api/crearEvento.
EndpointUna combinación concreta de ruta + verbo. GET /api/venues y POST /api/venues son dos endpoints en el mismo archivo.
CRUDCreate, Read, Update, Delete. Las cuatro operaciones básicas sobre un recurso, que mapean a POST, GET, PUT/PATCH y DELETE.
Payload / bodyEl cuerpo de la petición: los datos que manda el cliente. En Next lo leés con await request.json(), y llega tipado como any.
IdempotenciaQue repetir la misma petición dé el mismo resultado. GET y DELETE lo son; POST no — por eso apretar dos veces «comprar» puede generar dos tickets.
HandlerLa función que atiende un endpoint. En App Router son las funciones exportadas con el nombre del verbo dentro de route.ts.
MiddlewareCódigo que corre antes del handler para todas las rutas que coincidan: autenticación, logs, CORS.
SerializaciónConvertir un objeto de memoria a un formato transmisible, casi siempre JSON. Ojo: un Date serializado vuelve como string, y por eso en la ruta hacés new Date(body.date).

Testing y despliegue — lo que viene

TérminoTraducción práctica
Test unitarioPrueba una pieza aislada, sin base de datos ni red. Tus entidades son el caso ideal: Event.sellTicket() es lógica pura.
Test de integraciónPrueba que dos piezas reales se entiendan — por ejemplo el repositorio Drizzle contra un Postgres de verdad levantado en Docker.
Test E2EEnd to end. Recorre el flujo completo como lo haría una persona, desde la petición HTTP hasta la base. Playwright es la herramienta.

Arrange · Act · AssertLa estructura de un test legible: preparar el escenario, ejecutar la acción, comprobar el resultado. Un test que mezcla las tres cosas es difícil de leer cuando falla.
FixtureDatos de prueba preparados que varios tests reutilizan.
CoberturaQué porcentaje del código ejecutan tus tests. Útil para encontrar zonas sin probar, pésimo como meta en sí misma.
